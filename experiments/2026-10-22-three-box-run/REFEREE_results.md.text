## A. Three-box, ibm_marrakesh

Model fairness. NoiseModel.from_backend builds the readout error from the target's single `measure` error. For qubit 8 (FakeMarrakesh, same construction) the readout matrix is SYMMETRIC [[0.99365,0.00635],[0.00635,0.99365]]. It does NOT use prob_meas0_prep1 / prob_meas1_prep0. So the asymmetry is not in the model, and the question is fair to ask.
IBM's stated figures for probe qubit 8 at firing: prob_meas0_prep1 = 0.006592, prob_meas1_prep0 = 0.000244 (readout_error 0.00342). Applied to a post-selected probe-X read of a probe at <X>=0: offset = b - a = +0.0063, gain 1 - a - b = 0.9932. That is 8-14% of the observed offset (0.045-0.076). Adding it to the model gives difference +0.070, +0.051, +0.039 (each still above zero: about 6.7, 5.0, 3.8 SE).
Post-selection on s0=s1=0 with s0/s1 readout error (q6 b=0.0037, q7 b=0.0093): in the unused box the control never fires on the support, so the probe is |+> whatever the system state. Misassigned system shots therefore carry the same probe distribution; they cannot create an offset. Hard bound even if they carried <X>=1: contamination <= ~1.3% = 0.013. Not the source.
What the offset is not: readout asymmetry, post-selection leakage. What it may be (untested): coherent/ZZ/crosstalk and leakage that from_backend omits (the properties file lists zz terms; the model has none); calibration snapshot 11:46 EDT, fired 13:17 EDT, so staleness is not the issue. Cross-run support: +0.062 (fez 11 Oct), +0.060 (24 Sep), same sign in all three variants here.
Per-eps: hardware unused-box mean sits 0.03-0.10 at every eps; no eps dependence resolved.

R1. The P gap (+0.16/+0.17) is real against this model, but the positive boxes also fall short of the same model (V11 0.78/0.80 vs 0.90; V10 0.84/0.84 vs 0.90; VA 0.80 and 0.72 vs 0.90). R2 (G) is CONSISTENT in all three variants. So R1 is a model-versus-chip gain gap shared by all boxes, only somewhat larger on the negative box (~0.17 against 0.06-0.18). "Negative box less negative than model" is true but is not specific to the sign; the addendum's SIGN on one chip (-0.094 [-0.188,-0.001], null-world false SIGN rate noted by the addendum itself) is not a finding.
